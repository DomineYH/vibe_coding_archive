# EduVibe 아카이브 — 제품 요구사항 문서(PRD)

| 문서 정보 | 내용 |
|---|---|
| 버전 | 1.0 — 개발 착수 기준안 |
| 작성일 | 2026-09-22 |
| 제품 | 교사가 만든 교육용 웹 앱과 제작 프롬프트를 공유하는 아카이브 |
| 구현 기반 | FastAPI + React + SQLite 3 |
| 개발 순서 | 기존 UI/UX 구동 → 읽기 API → 인증 → 앱 관리 → 관리자 기능 → 실제 연결 검사 → 배포 |
| 화면 기준 | 첨부 HTML·JSX의 구조·스타일·동작. 새 디자인을 제작하지 않는다. |
| 검증 범위 | 첨부 소스와 축소 미리보기 검토. 실제 브라우저 시각 비교·기능 테스트는 개발 단계에서 수행해야 한다. |

> **제품 목표:** 기존 EduVibe 화면을 유지하면서, 브라우저 내부 데모를 여러 사용자가 실제로 사용하는 서버·DB 기반 서비스로 전환한다. 첫 번째 완료 결과물은 백엔드 없이 모든 주요 화면과 상호작용을 확인할 수 있는 프론트엔드다.

## 1. 요구사항의 우선순위와 결정 상태

### 1.1 사용자 명시 요구 — 고정

| ID | 고정 요구사항 |
|---|---|
| FIX-01 | 백엔드는 FastAPI를 사용한다. |
| FIX-02 | DB는 SQLite 3를 사용한다. |
| FIX-03 | 프론트엔드는 React를 우선한다. 본 PRD에서는 기존 JSX 재사용을 위해 React를 채택한다. |
| FIX-04 | 회원가입 필수 정보는 아이디·비밀번호·별명이다. 이메일·연락처는 선택 정보다. |
| FIX-05 | 제공된 UI/UX를 유지한다. 레이아웃이나 시각 스타일을 새롭게 설계하지 않는다. |
| FIX-06 | 개발의 처음은 UI/UX 구동이다. 실제 기능은 이후 하나씩 연결하고 검증한다. |

### 1.2 첨부본에서 유지하는 제품 정책

공개 앱은 비로그인 상태에서도 열람한다. 회원가입은 관리자 승인 대기 상태로 시작하고, 승인 후 로그인할 수 있다. 승인된 회원은 자신의 앱을 등록·편집·삭제한다. 비공개 앱은 작성자와 관리자만 열람한다. 관리자는 사용자 승인·승인 해제·비밀번호 변경·계정 삭제와 전체 앱 관리를 수행한다. 개별 앱 연결 재확인 및 관리자 전체 재검사 흐름도 유지한다.

근거: `app.jsx`의 `login`, `signup`, `toggleApprove`, `deleteUser`, 라우트 가드; 각 `view-*.jsx`.

### 1.3 원본에 없는 정책 — 이 문서의 제안 기본값

비밀번호 길이, 로그인 아이디 형식, 별명 중복 허용, 세션 유효기간, 검색 정렬, 페이지 크기, 검사 제한, 백업 주기, 성능 목표는 첨부본만으로 확정할 수 없다. 본 문서는 개발을 멈추지 않도록 기본값을 제안하며, 이를 사용자 확정 사항으로 간주하지 않는다. 변경 시 해당 요구사항과 테스트를 함께 수정한다.

충돌 시 적용 순서는 **사용자의 명시 요구 → 문서에 열거한 필수 변경 → 첨부 UI/UX → 제안 기본값**이다. 새로운 기능이나 디자인 변경은 별도 승인 없이 추가하지 않는다.

## 2. 첨부 소스 분석

### 2.1 파일별 역할

| 첨부 파일 | 현재 역할 | 실제 서비스 전환 방향 |
|---|---|---|
| `EduVibe 아카이브.html` | 진입 HTML, Tailwind 색상 확장, 글꼴, 전역 CSS, CDN 의존성 | Vite 진입점·로컬 CSS 빌드로 옮기되 시각 결과 유지 |
| `app.jsx` | 상태, 화면 전환, 로그인, 가입, 앱 저장, 관리자 작업, 알림 | 화면 셸 유지; 도메인 동작을 비동기 서비스 호출로 교체 |
| `data.jsx` | 과목·학년·테마, 샘플 사용자·앱, 무작위 Ping | 상수와 개발용 fixture 분리; 운영 DB 자동 주입 금지 |
| `ui.jsx` | 버튼, 필드, 배지, 카드, 썸네일, 복사, 빈 화면 | 재사용; 접근성과 실제 비동기 상태 지원 |
| `view-auth.jsx` | 로그인·회원가입, 데모 계정 안내 | 별명·선택 정보 추가, 실제 인증 연동 |
| `view-gallery.jsx` | 공개 범위, 과목·학년·검색, 카드 그리드 | 서버의 접근 가능 목록과 검색 결과 사용 |
| `view-detail.jsx` | 앱 열기, 설명, 프롬프트, 스택, 연결 상태, 편집·삭제 | 상세 API·권한·실제 검사 결과 연결 |
| `view-submit.jsx` | 등록·수정, 학년 다중 선택, 테마 미리보기, 공개 설정 | 폼 유지; 서버 검증 및 저장 연결 |
| `view-admin.jsx` | 사용자 관리, 통계, Health Monitor | 관리자 API와 실제 통계·작업 결과 연결 |
| `tweaks-panel.jsx` | 외부 편집 호스트와 통신하는 디자인 조절 패널 | 개발용으로 격리; 운영에서는 원본 기본값 고정 |

### 2.2 서비스 전환 시 반드시 구분할 사항

| 현재 소스에서 확인한 사항 | PRD 반영 |
|---|---|
| `users`, `apps`, `currentUserId`를 localStorage에 저장한다. | 운영 데이터와 인증의 원본은 서버·SQLite다. localStorage를 인증 수단으로 사용하지 않는다. |
| 사용자 비밀번호가 `pw` 평문이고, 브라우저에서 비교한다. | 서버에서 비밀번호 해시를 검증한다. 사용자 목록 응답에 비밀번호·해시를 넣지 않는다. |
| 아이디가 로그인 식별자이자 공개 작성자 이름이다. | 내부 사용자 ID·로그인 아이디·공개 별명을 분리한다. |
| 가입 폼은 아이디·비밀번호·비밀번호 확인만 받는다. | 별명 필수, 이메일·연락처 선택 입력을 같은 폼 스타일로 추가한다. |
| 안내문에 ‘별도의 개인정보는 받지 않아요’가 있다. | 새로운 수집 항목에 맞게 수정한다. 원문을 그대로 두지 않는다. |
| `simulatePing()`은 무작위로 200·404·500을 만든다. | 운영 연결 상태는 실제 HTTP 검사 결과만 사용한다. |
| `StatusBadge`와 상세 화면은 알 수 없는 상태를 200 메타데이터로 대체한다. 관리자 화면은 일부 미정의 상태에서 오류가 날 수 있다. | 미검사·시간 초과·네트워크 실패·기타 HTTP 코드를 명시적으로 처리한다. 정상으로 추정하지 않는다. |
| 상세 화면은 검사 시점을 항상 ‘오늘’로 표시한다. | 실제 날짜·시간과 미검사 상태를 표시한다. |
| 프론트엔드의 편집 경로·저장 함수 자체에는 완전한 소유권 검사가 없다. | 상세 버튼 노출과 별개로 모든 쓰기 API에서 작성자·관리자 권한을 검증한다. |
| 썸네일은 외부 사이트의 캡처가 아니라 테마 그라데이션과 앱 이름으로 만든 화면이다. | 같은 생성 방식을 유지한다. 자동 캡처·이미지 업로드를 추가하지 않는다. |
| `TweaksPanel`은 메시지로 열리는 개발 도구다. | 일반 사용자용 테마 설정 기능으로 오해해 제품 범위에 넣지 않는다. |

샘플 앱의 URL과 설명은 테스트 데이터다. 실제 서비스 가동 여부나 교육적 효과를 검증한 자료가 아니며, 샘플에 등장하는 앱 자체를 개발하는 프로젝트도 아니다.

## 3. 제품 범위

### 3.1 이번 버전에 포함

기존 갤러리, 로그인·회원가입, 앱 상세, 앱 등록·편집, 관리자 사용자 관리, 관리자 Health Monitor를 모두 구현한다. 회원 정보 확장, SQLite 영속화, 서버 권한 검사, 안전한 외부 URL 검사, 오류 처리와 배포·백업을 포함한다.

### 3.2 이번 버전에서 제외

교육용 앱의 소스 실행·호스팅·자동 배포, LLM API 호출이나 프롬프트 자동 생성, 파일 업로드, 웹 페이지 캡처, 외부 사이트 iframe 실행, 댓글·좋아요·평점·북마크, 소셜 로그인, 이메일·문자 인증/발송, 일반 프로필 편집 페이지, 자동 주기 모니터링, 다중 서버 확장은 제외한다.

이메일·연락처를 입력받는다고 해서 인증·알림·자동 비밀번호 복구 기능까지 포함되는 것은 아니다. ‘앱 열기’는 등록된 외부 URL을 새 탭에서 여는 기능이다.

### 4.2 허용하는 변경 — 범위를 명시하고 검수한다

| 변경 ID | 변경 내용 | 이유 |

| UI-D08 | 선택 정보의 비공개 안내와 필요한 개인정보 안내 영역 | 새 수집 항목의 설명 필요 |
| UI-D09 | 대량 목록의 하단 점진 로딩·실패 재시도 | 기존 연속 카드/목록 스크롤 형태 유지 |

추가 필드 때문에 회원가입 카드의 세로 길이가 늘어나는 것은 허용하지만, 2열 가입 폼·새로운 모달형 가입·새 디자인 시스템으로 바꾸지 않는다. 필수 변경 외의 시각 차이는 별도 이슈로 남기고 승인 없이 수용하지 않는다.

원본은 작은 화면에서 상단 메뉴 일부를 숨긴다. 새 햄버거 메뉴를 임의로 만들지 않는다. 모바일 관리자 진입은 `/admin` 직접 경로를 지원하며, 모바일 메뉴 신설은 별도 승인 사항이다.

### 4.3 시각 검수 방법

Phase 1에서 원본의 실행 가능한 로컬 기준 화면을 먼저 확보한다. 축소 미리보기만으로 간격·글꼴·배지 표현을 추정하지 않는다. 원본 코드와 미리보기가 다르면 `docs/ui-deviations.md`에 차이를 기록하고, JSX/CSS의 실제 렌더링을 우선 기준으로 삼되 사용자 확인 대상임을 명시한다.

동일 브라우저·글꼴 로딩·DPR·데이터·시간 조건에서 원본과 이식본을 비교한다. 1440×1000, 1024×900, 768×1024, 390×844 화면을 검수하고 360px 폭에서도 가로 넘침을 확인한다. 화면별 전체 캡처와 핵심 컴포넌트 캡처를 저장한다. 시간·커서·로딩 애니메이션은 고정하거나 마스킹한다.

출시 조건은 ‘승인되지 않은 레이아웃·색상·글꼴·정보 순서 차이 0건’이다. 자동 이미지 비교 허용 오차는 동일 렌더링 환경에서 캘리브레이션하고 기록한다. 근거 없는 고정 유사도 수치만으로 합격시키지 않는다.

## 5. 기술 구성과 경계

| 계층 | 채택안 | 적용 원칙 |
|---|---|---|
| 프론트엔드 | React + Vite | 기존 React JSX를 옮긴다. 프레임워크 교체는 하지 않는다. |
| 타입 | TypeScript | 서비스·API 계약부터 적용한다. 기존 JSX의 일괄 TSX 변환이 첫 구동을 막지 않게 한다. |
| 스타일 | 빌드형 Tailwind CSS + 원본 전역 CSS | 원본 커스텀 색상·임의 값·브레이크포인트의 렌더링을 보존한다. |
| 아이콘 | `lucide-react` | 원본 아이콘을 정상 import한다. 빈 아이콘 폴백으로 오류를 숨기지 않는다. |
| 라우팅 | React Router | 화면 디자인을 바꾸지 않고 주소·history를 연결한다. |
| 서버 데이터 | TanStack Query + 서비스 모듈 | 로딩·캐시·재조회·변경 후 갱신을 중앙화한다. |
| 백엔드 | FastAPI + Pydantic | REST API, 입력/출력 스키마, 서버 권한 검증 |
| DB 접근 | SQLAlchemy 2 계열 + Python `sqlite3` 드라이버 | SQLite를 다른 DB로 바꾸는 의미가 아니다. 요청/작업 단위 세션 사용 |
| 스키마 변경 | Alembic | 운영 DB는 명시적 migration으로 변경 |
| 비밀번호 | `pwdlib`의 Argon2 계열 구현 | 운영 해시 파라미터는 검증된 권장값과 서버 실측을 기준으로 고정 |
| 외부 HTTP | HTTPX + 검증된 outbound 보호 계층 | HTTPX 사용 자체를 SSRF 방어로 간주하지 않는다. |
| 도구 | Python 의존성은 uv, 프론트엔드는 npm | `uv.lock`, `package-lock.json` 커밋 |
| 테스트 | pytest, Vitest/React Testing Library, Playwright | API·컴포넌트·E2E·시각 회귀 분리 |

React 공식 문서는 Vite 기반 시작과 별도 라우팅·서버 데이터 도구 구성을 설명한다[R01]. FastAPI는 특정 ORM을 강제하지 않고 SQLite 연결을 지원한다[R02]. 이 프로젝트에서는 기존 JSX 재사용과 FastAPI와의 역할 분리를 근거로 React SPA를 선택한다. SSR·SEO·서버 컴포넌트 요구가 없는 현재 범위에서는 Next.js나 Jinja2로 화면을 다시 만들 이유가 없다.

원본 HTML은 React 18.3.1 CDN과 브라우저 Babel을 사용한다. 이는 입력 소스의 버전이지 운영 권장 최신 버전이라는 뜻이 아니다. Phase 1은 원본 호환성을 우선하고, 운영 의존성은 구현 시점에 호환성·보안 상태를 확인해 정확한 버전으로 잠근다. UI 이식과 대규모 React/Tailwind 업그레이드를 같은 작업으로 묶지 않는다. Tailwind Play CDN은 운영용으로 제공되지 않으므로 로컬 빌드로 전환한다[R03].

운영 구조는 `브라우저 → 동일 출처의 정적 React 파일 및 /api/v1 → FastAPI → SQLite`다. 개발에서는 Vite가 `/api`를 FastAPI에 프록시한다. 초기 운영은 단일 호스트의 API 프로세스와 별도 연결 검사 worker를 기본으로 한다.

## 6. 사용자·인증·권한 요구사항

### 6.1 회원 정보 계약 — AUTH-01

| 필드 | 필수 | 제안 검증 규칙 | 공개 범위 |
|---|---|---|---|
| `login_id` | 필수 | 2~32자. 한글 완성형·영문·숫자·`_-.` 허용. 앞뒤 공백 제거, NFC 정규화. 중복 판정은 정규화+casefold 키 사용 | 본인·관리자 |
| `password` | 필수 | 15~128자. 유니코드·공백 허용. 임의 조합 강제·자동 절단·trim 금지 | 저장·반환 금지; 해시만 DB에 저장 |
| `password_confirm` | 가입 UI 필수 | 비밀번호 일치 확인 | 브라우저 검증 전용, DB 저장 금지 |
| `nickname` | 필수 | 2~20자, 앞뒤 공백 제거, 줄바꿈/제어문자 금지. 중복 허용 | 작성자 표시 등 공개 |
| `email` | 선택 | 미입력·공백만 입력하면 NULL. 입력 시 이메일 형식, 최대 254자. 본인 인증 기능 없음 | 본인·권한 있는 관리자 |
| `phone` | 선택 | 미입력은 NULL. `+`, 숫자, 공백, 하이픈 허용; 숫자 기준 7~15자리, 원본 최대 32자. 통신사/국가 실재성 인증은 하지 않음 | 본인·권한 있는 관리자 |

별명은 로그인 수단이 아니며, 별명이 같은 회원도 서로 다른 내부 사용자 ID로 구분한다. 비밀번호 최소 15자는 MFA를 제공하지 않는 본 버전에 적용하는 보안 제안값이며 원본의 ‘4자 이상’을 유지하지 않는다[R04]. 가입 폼과 관리자 초기화 입력에 같은 정책을 적용한다. 알려진 흔한 비밀번호 차단을 적용하되 비밀번호 원문을 외부 서비스에 보내지 않는다.

기존 데모의 한글 아이디는 로그인 아이디로 그대로 사용할 수 있다. 개발 fixture는 기존 표시 이름을 별명으로 복제하고 내부 UUID를 새로 부여한다. 운영 계정을 기존 localStorage나 데모 데이터에서 자동 생성하지 않는다.

### 6.2 가입·로그인 — AUTH-02~04

- **AUTH-02 가입:** 역할은 서버에서 `user`, 승인 상태는 `false`로 지정한다. 가입 요청에 `role`, `approved`, 내부 ID가 들어오면 거부한다. DB UNIQUE 제약으로 동시 중복 가입도 방지한다. 성공 후 로그인 화면으로 전환하고 승인 대기를 안내한다. 자동 로그인하지 않는다.
- **AUTH-03 로그인:** 아이디·비밀번호를 검증한 다음 승인 여부를 확인한다. 자격증명 실패는 동일 메시지를 반환한다. 정확한 비밀번호를 확인한 승인 대기 계정에만 승인 대기 안내를 반환한다. 승인 회원은 로그인 후 갤러리 또는 허용된 내부 복귀 경로로 이동한다.
- **AUTH-04 세션:** 서버 저장형 세션과 HttpOnly 쿠키를 사용한다. 로그인 시 세션 식별자를 교체하고, 로그아웃 시 서버 세션을 폐기한다. 새로고침 시 `/auth/me`로 로그인 상태를 복원한다. 제안 절대 유효기간은 8시간이며 로그인 유지 UI는 추가하지 않는다.

운영 쿠키는 `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, Domain 미지정을 적용한다. 운영 쿠키명은 `__Host-eduvibe_session`을 사용하고, 로컬 HTTP 개발은 별도 이름과 명시적 개발 설정을 쓴다. 인증 토큰을 localStorage/sessionStorage에 넣지 않는다[R05]. 쿠키만으로 모든 CSRF 위험이 해결되는 것은 아니므로 상태 변경 요청에는 세션 결합 CSRF 토큰과 Origin 검사를 적용한다[R06]. 로그인·가입·익명 사용자의 검사 요청에도 적용한다.

### 6.3 승인·비밀번호 초기화 — AUTH-05~06

승인 해제 시 대상 사용자의 기존 세션을 모두 무효화한다. 이후 요청마다 서버가 사용자의 존재·승인·역할을 다시 확인한다. 승인 해제만으로 해당 사용자의 기존 공개 앱을 숨기지는 않는다. 이는 원본 공개 범위 정책을 유지하는 결정이다.

관리자는 원본 인라인 비밀번호 변경 영역에서 일반 회원의 임시 비밀번호를 지정한다. 입력은 `type=password`로 마스킹하고 적용 후 즉시 지운다. 서버는 해시만 저장하고 모든 기존 세션을 폐기한다. **제안 보완:** `must_change_password=true`를 설정하고 다음 로그인에서는 15분 유효의 비밀번호 변경 전용 세션만 발급한다. 기존 인증 카드 안에 새 비밀번호·확인 입력을 표시하며, 변경 완료 전에는 회원/관리자 작업을 허용하지 않는다. 일반 프로필 페이지를 새로 만들지 않는다.

비밀번호 분실은 운영자의 별도 본인 확인 후 위 절차로 처리한다. 선택 입력된 이메일·전화번호만으로 본인이라고 자동 판단하지 않으며 자동 메일/문자는 발송하지 않는다. 초기 관리자 생성·관리자 계정 복구는 서버의 대화형 CLI로 처리한다. 고정 관리자 비밀번호를 코드나 `.env.example`에 넣지 않는다.

### 6.4 인증 남용 방지 — AUTH-07

로그인 실패는 계정 키+IP 조합과 IP 전체에 각각 제한을 적용한다. 제안값은 조합당 15분간 10회 실패, IP당 15분간 200회 실패이며 429와 재시도 시점을 반환한다. 가입은 IP당 시간당 100회 요청을 초기 제한으로 삼되 학교 공동망 등 정상 이용을 고려해 조정한다. 영구 계정 잠금으로 타인의 계정을 쉽게 방해할 수 있게 만들지 않는다.

존재하지 않는 아이디도 더미 해시 검증을 수행해 계정 존재 여부에 따른 시간 차이를 줄인다[R13]. 해싱 동시 실행 수와 요청 본문 크기를 제한한다. 속도 제한 기록은 최소한의 식별 키와 짧은 만료 기간만 사용하며 비밀번호·연락처를 기록하지 않는다.

### 6.5 권한표 — ACL-01

‘승인 대기’에는 승인 해제된 일반 계정을 포함한다. 이 계정은 로그인 세션을 얻을 수 없으므로 앱 열람은 비회원과 같다.

| 작업 | 비회원/승인 대기 | 승인된 일반 회원 | 관리자 |
|---|---|---|---|
| 공개 앱 목록·상세·프롬프트 복사·앱 열기 | 허용 | 허용 | 허용 |
| 자신의 비공개 앱 열람 | 불가 | 허용 | 허용 |
| 타인 비공개 앱 열람 | 불가 | 불가 | 허용 |
| 앱 신규 등록 | 불가 | 허용 | 허용 |
| 자신의 앱 편집·삭제·공개 전환 | 불가 | 허용 | 허용 |
| 타인 앱 편집·삭제 | 불가 | 불가 | 허용 |
| 열람 가능한 앱의 개별 연결 재검사 | 제한적 허용 | 제한적 허용 | 제한적 허용 |
| 전체 연결 재검사 | 불가 | 불가 | 허용 |
| 사용자 목록·승인·비밀번호 초기화·계정 삭제 | 불가 | 불가 | 일반 회원 대상으로 허용 |
| 관리자 계정 삭제·승인 해제·관리자 비밀번호 초기화 API | 불가 | 불가 | 제공하지 않음; 서버 CLI 별도 |

비공개 앱의 존재·작성자·분류·검사 정보는 비권한 사용자에게 노출하지 않는다. 해당 상세/검사 API는 동일한 404를 반환한다. 공개 앱의 무권한 편집은 인증 여부에 따라 401 또는 403이다. 일반 회원이 관리자 API를 직접 호출하면 403이다. 프론트엔드에서 버튼을 숨기는 것은 보안 경계가 아니다.

## 7. 화면별 기능 요구사항

### 7.1 공통 셸·탐색 — UI-01~03

`Header`, 기존 footer, 토스트를 유지한다. 헤더 회원 표시는 별명으로 변경하고 관리자 배지는 서버 역할에 따라 표시한다. 작성자 아바타는 별명 첫 글자를 사용한다. 버튼·입력 필드의 비활성/로딩 처리는 공용 컴포넌트에서 통일한다.

| URL | 화면 | 동작 |
|---|---|---|
| `/` | 갤러리 | 필터·검색을 query string과 동기화 |
| `/auth?mode=login` | 로그인 | 기본 진입 |
| `/auth?mode=signup` | 회원가입 | 기존 세그먼트로 전환 |
| `/auth?mode=password-change` | 초기화 후 비밀번호 변경 | 유효한 제한 세션이 있을 때만 허용 |
| `/apps/:appId` | 상세 | 접근 권한 확인 |
| `/apps/new` | 등록 | 승인된 회원 |
| `/apps/:appId/edit` | 편집 | 작성자 또는 관리자 |
| `/admin?tab=users` | 사용자 관리 | 관리자 |
| `/admin?tab=health` | Health Monitor | 관리자 |

`/apps/new`를 앱 ID로 해석하지 않는다. 상세에서 ‘갤러리로’ 이동할 때 검색·분류 조건을 복원한다. 브라우저 뒤로가기·앞으로가기·직접 진입·새로고침을 지원한다. 허용되지 않은 `return_to` 외부 URL로 이동하지 않는다. 잘못된 경로는 기존 EmptyState 스타일의 안내를 사용한다.

### 7.2 갤러리 — GAL-01~04

공개 앱과 로그인 사용자가 볼 수 있는 비공개 앱만 서버에서 조회한다. 필터는 과목 1개·학년 1개·검색어를 AND로 결합한다. 검색 대상은 앱 이름·작성자 별명·상세 설명이며 로그인 아이디·이메일·연락처는 검색에 사용하지 않는다.

과목 상수는 `수학, 과학, 영어, 역사, 국어, 사회, 정보, 기타`, 학년은 `초1~초6, 중1~중3, 고1~고3` 순서를 유지한다. 과목 탭에는 ‘전체’와 사용자가 열람 가능한 앱에서 사용 중인 과목만 표시한다. 이 목록은 현재 페이지가 아니라 **접근 가능한 전체 집합**을 기준으로 계산하며, 검색어·학년 필터 때문에 임의로 사라지지 않는다.

제안 기본 정렬은 `created_at DESC, id DESC`, 기본 페이지 크기는 24개다. 원본 mock 시각 비교에서는 원본 fixture 순서를 고정한다. API 모드에서는 기존 연속 스크롤 형태로 다음 페이지를 점진 로딩한다. 별도 정렬 드롭다운·페이지 번호 UI는 추가하지 않는다.

검색어는 최대 100자, 300ms debounce를 제안한다. 한글 입력 조합 중에는 검색을 확정하지 않는다. 문자열 검색은 정규화된 키와 매개변수 SQL로 수행하고 `%`, `_`는 문자 그대로 검색하도록 이스케이프한다. 이전 검색 요청이 늦게 도착해 최신 결과를 덮어쓰지 않게 한다. 최초 로딩·검색 결과 없음·통신 실패를 구분한다.

### 7.3 앱 상세 — APP-01

기존 정보 순서를 유지한다. 이름·별명·과목·학년·공개 범위, 테마 썸네일, 상세 설명/활용 매뉴얼, 핵심 프롬프트와 복사, 기술 스택 4개, 연결 상태·검사 시점·등록일을 표시한다.

설명·프롬프트·별명은 텍스트로 렌더링한다. 임의 HTML을 실행하거나 미리보기로 삽입하지 않는다. 프롬프트 개행과 코드 블록 스크롤을 유지한다. 복사 실패 시 ‘복사됨’을 표시하지 않고 같은 알림 체계로 실패를 안내한다.

외부 앱은 새 탭으로 열고 `noopener noreferrer`를 적용한다. 아카이브에서 ‘비공개’로 바꾸는 것은 등록 정보의 열람 제한이지, 외부 배포 사이트 자체에 인증을 추가하는 것이 아니다. 이를 공개 범위 설정의 안내로 설명한다.

### 7.4 등록·편집 — APP-02~04

| 필드 | 필수 | 제안 규칙 |
|---|---|---|
| 앱 이름 | 필수 | 공백 제외 유효 내용, 최대 100자 |
| 배포 URL | 필수 | 최대 2048자, 절대 `http`/`https` URL, 사용자 정보 포함 URL 금지 |
| 핵심 프롬프트 | 필수 | 공백만 입력 불가, 최대 30,000자 |
| 상세 설명·활용 매뉴얼 | 필수 | 공백만 입력 불가, 최대 20,000자 |
| 과목 | 필수 | 정의된 과목 중 1개 |
| 적용 학년 | 필수 | 정의된 학년 중 1~12개, 중복 제거·정의된 순서로 표시 |
| 기술 스택 | 선택 | DB·백엔드·프론트엔드·호스팅, 항목당 최대 200자 |
| 공개 여부 | 필수 | 원본과 같은 기본값 `true` |
| 썸네일 테마 | 필수 | 원본 8개 중 하나, 기본값 `niagara` |

URL은 파싱 후 검증하며 브라우저와 서버에서 같은 허용 정책을 사용한다. 명백한 localhost·사설 IP·사용자 정보·비허용 포트 URL은 등록 단계에서 거부한다. IPv4-mapped/compatible IPv6의 내장 IPv4에도 기존 IPv4 차단 대역을 적용하며 공개 내장 IPv4는 허용한다. 빈 사용자 정보도 파서가 authority로 해석하는 모든 표기에서 거부하되 경로·query·fragment의 `@`는 허용한다. DNS 실패나 대상 사이트의 404만으로 등록 자체를 막지는 않는다. 이후 검사 단계에서는 DNS 및 네트워크 목적지를 다시 검증한다. URL fragment는 앱 열기에는 유지할 수 있지만 HTTP 검사에는 전송하지 않는다.

이름·과목·학년·테마 변경은 현재 미리보기에 즉시 반영한다. 썸네일은 기존 `DeviceScreen`으로 생성한다. 작성자는 서버 세션에서 결정하며 요청 본문의 작성자·상태·등록일을 신뢰하지 않는다. 앱에 적는 기술 스택은 소개 텍스트이며 아카이브 플랫폼의 기술 구성을 바꾸지 않는다.

저장 성공을 서버에서 확인한 뒤 상세로 이동한다. 실패하면 입력값을 보존하고 오류를 표시한다. 중복 클릭을 차단하고 생성 요청에는 재시도용 idempotency key를 사용한다. 변경·삭제는 버전 충돌을 409로 알리며, 다른 사용자의 최신 변경을 조용히 덮어쓰지 않는다. 미저장 이탈은 현재 디자인에 맞는 확인 또는 브라우저 이탈 경고로 처리한다.

새 앱의 초기 연결 상태는 `unchecked`다. URL 변경 시 `url_version`을 증가시키고 이전 연결 상태를 초기화한다. URL이 아닌 정보만 바꾸면 기존 검사 결과를 유지한다.

### 7.5 앱 삭제·공개 범위 — APP-05~06

삭제 버튼의 기존 인라인 확인/취소 UI를 유지한다. 작성자와 관리자만 삭제할 수 있다. 삭제 성공 후 갤러리로 이동하고 목록·상세·관리자 통계를 갱신한다. 삭제된 앱의 학년·연결 상태·미완료 검사 작업도 제거하거나 취소하며, 늦게 도착한 검사 응답으로 앱이 복구되어서는 안 된다.

공개→비공개 변경은 이후 서버 조회에 즉시 반영한다. 권한이 없는 사용자에게 캐시된 상세·목록을 새로 반환하지 않는다. 이미 타인이 읽거나 복사한 내용까지 회수할 수 있다는 보장은 하지 않는다.

### 7.6 관리자 — ADM-01~05

통계 카드 4개를 유지한다. 전체 사용자·승인 대기·등록된 앱·정상 가동 값을 서버 집계로 표시한다. 관리자 집계는 공개/비공개 앱 모두를 포함한다. 한 페이지에 표시된 행 수로 전체 통계를 계산하지 않는다.

사용자 목록은 승인 대기 우선, 같은 상태에서는 최신 가입 순을 제안한다. 별명을 주요 표시로, 로그인 아이디와 가입일을 기존 보조 정보 영역에 표시한다. 각 행에서 승인/승인 해제, 비밀번호 초기화, 삭제를 수행한다. 이메일·연락처를 공개 갤러리에 노출하지 않으며, 관리자 사용 목적과 접근 정책이 정해지기 전에는 새 연락처 관리 화면을 만들지 않는다.

계정 삭제 확인에는 대상 별명/아이디와 함께 삭제될 앱 수를 표시한다. 삭제 직전에 앱 수가 바뀌면 409로 재확인을 요구한다. 계정·앱·학년·세션·검사 데이터 정리는 하나의 짧은 DB 트랜잭션으로 수행한다. 관리자 계정 대상의 금지 작업은 UI뿐 아니라 API에서도 거부한다.

비밀번호 초기화와 계정 삭제는 제안 정책으로 ‘최근 15분 이내 로그인한 관리자 세션’을 요구한다. 부족하면 기존 인증 화면에서 재로그인하도록 안내하고, 비밀번호를 URL이나 localStorage에 임시 저장하지 않는다.

Health Monitor는 앱별 URL·상태·검사 결과·개별 재검사·전체 재검사·삭제를 제공한다. 오류 메시지는 실제 관찰 결과와 가능한 원인을 구분한다. 단지 HTTP 500이라는 이유만으로 환경변수 누락·DB 고장을 확정하지 않는다.

## 8. 실제 연결 검사 요구사항

### 8.1 제품 의미 — HLT-01

화면에 남아 있는 ‘Ping’은 HTTP 연결 확인을 뜻하며 ICMP ping은 구현하지 않는다. 브라우저에서 타사 URL을 직접 fetch해 판정하지 않고 서버의 전용 worker가 검사한다. 정상 결과는 ‘등록 URL이 검사 시점에 HTTP 응답했다’는 뜻이다. 앱 내부 로그인·버튼·AI 응답·학습 기능의 정상 작동까지 보증하지 않는다.

최초 버전은 **수동 개별 검사와 관리자 전체 검사만** 제공한다. 단순 페이지 열람으로 무조건 외부 검사를 발생시키지 않는다. 자동 정기 검사와 장애 알림은 후속 범위다. 검사 worker가 외부 요청을 보내는 출처와 책임 범위는 운영 정책에 포함한다.

### 8.2 결과 모델 — HLT-02

검사 작업 상태와 마지막 완료 결과를 구분한다.

| 마지막 결과 `state` | HTTP 코드 | 표시 의미 |
|---|---|---|
| `unchecked` | NULL | 미검사 |
| `healthy` | 실제 2xx | 해당 검사 시점에 정상 HTTP 응답 |
| `http_error` | 실제 4xx/5xx 등 | 대상이 해당 HTTP 오류를 반환함 |
| `timeout` | 응답이 없으면 NULL | 전체 검사 제한 시간 초과 |
| `network_error` | NULL | DNS·TLS·연결 실패; 관리자에게 구체 분류 |
| `blocked` | NULL | 아카이브의 보안 정책상 검사할 수 없음 |
| `redirect_error` | 있으면 실제 마지막 3xx | 허용 횟수 초과·유효하지 않은 리다이렉트 |

`job_status`는 `queued/running/completed/failed/cancelled`로 관리한다. 검사 중에도 마지막 완료 결과와 그 검사 시점은 보존한다. queue/worker 실패와 대상 앱의 HTTP 실패를 같은 값으로 저장하지 않는다. 예를 들어 대상의 404를 확인한 작업은 작업 자체는 `completed`, 결과는 `http_error`다.

기존 초록/붉은 배지 형태를 유지하고, 미검사·정책상 차단·오래된 결과에는 기존 중립/황색 톤을 활용한다. 미검사를 오류나 정상으로 세지 않는다. 일반 사용자에게는 간단한 상태 안내, 관리자에게는 실제 코드·응답 시간·오류 분류를 제공한다. 404/500에 임의의 `timeout`을 표시하지 않는다.

`checked_at`은 UTC 전체 시각으로 저장하고 기본 `Asia/Seoul`로 표시한다. NULL은 ‘검사 이력 없음’, 오늘만 ‘오늘 HH:mm’, 다른 날짜는 날짜와 시각을 표시한다. 제안 신선도는 15분이며 그보다 오래된 결과는 ‘재확인 필요’를 알린다. ‘정상 가동 X/N’의 X는 **신선한 healthy 결과의 수**, N은 현재 전체 앱 수다. 실시간 가동률이라고 해석하지 않도록 안내한다.

### 8.3 검사 실행 — HLT-03

처음에는 HEAD를 사용하고 405 또는 501일 때만 제한된 GET으로 대체한다. GET은 본문 전체를 읽지 않고 응답 헤더 확인 후 스트림을 닫는다. 응답 본문·쿠키·외부 스크립트를 실행·저장하지 않는다. TLS 검증을 끄지 않는다.

제안값은 연결 timeout 3초, DNS·리다이렉트·HEAD/GET 대체를 합한 전체 deadline 10초, 리다이렉트 최대 5회, 동시에 검사할 앱 최대 3개다. HTTPX의 개별 connect/read timeout만 설정하고 전체 10초 제한이 구현됐다고 간주하지 않는다[R10]. 네트워크 실패의 자동 반복 검사는 하지 않는다.

개별 검사는 해당 앱을 읽을 수 있는 사용자만 요청할 수 있다. 원본의 비회원 재검사 기능은 유지하되, 실제 외부 요청은 앱당 60초 cooldown과 사용자/익명 IP 기준 분당 10회 요청 제한을 적용한다. 관리자 전체 검사는 5분 cooldown, 동시에 활성 배치 1개를 기본으로 한다. 중복 검사 요청은 기존 작업을 반환하고 새 네트워크 요청을 만들지 않는다. 전체 검사도 앱별 cooldown·보안 검사·동시성 제한을 우회하지 않는다.

### 8.4 SSRF 방어 — HLT-04, 운영 공개 차단 조건

사용자가 등록한 URL을 서버가 호출하는 기능은 SSRF 공격 경로가 된다. 아래 사항은 단순 URL 정규식보다 넓은 검증을 요구한다[R09].

1. 호출 API는 URL 문자열이 아니라 `app_id`만 받는다. 서버가 접근 권한을 확인하고 DB에 저장된 URL을 사용한다. `http/https`, 80/443 포트만 허용하고 userinfo를 금지한다.
2. DNS A/AAAA의 모든 후보를 확인한다. loopback·private·link-local·multicast·unspecified·reserved·클라우드 메타데이터·서비스 내부 IP는 거부한다. IPv6, IPv4-mapped IPv6, 비정상 IP 표기 우회도 시험한다.
3. 사전 DNS 검증 후 HTTP 라이브러리가 다른 IP로 재해석해 연결하는 TOCTOU/DNS rebinding을 막는다. 검증 IP로 연결을 고정하는 검증된 transport 또는 동일 정책을 강제하는 outbound proxy를 사용하고 원래 호스트의 Host/SNI·TLS 검증을 유지한다.
4. 자동 리다이렉트를 끈다. 각 Location을 같은 파서로 해석하고 목적지·포트·DNS/IP를 다시 검증한 뒤 명시적으로 이동한다. 단순히 `follow_redirects=True`를 켜지 않는다.
5. 세션 쿠키·인증 헤더·내부 프록시 자격증명을 외부로 전달하지 않는다. 서로 다른 검사 간 쿠키를 공유하지 않는다. 환경 프록시를 무의식적으로 상속하지 않는다.
6. 앱 코드의 검사와 별도로 네트워크 수준에서 내부망·호스트 내부 서비스·메타데이터 접근을 차단한다. 응답/헤더 크기, 요청 수, 전체 시간과 worker 동시성을 제한한다.

이 방어를 구현·검증하지 못한 환경에서는 실제 외부 검사 기능을 켜지 않는다. 운영 전에는 모의 transport로 정책을 시험하고, 개발/CI가 실제 사설망이나 메타데이터 서버를 호출하지 않도록 한다.

### 8.5 작업 지속성·경합 — HLT-05

수동/전체 검사 요청은 SQLite 작업 큐에 기록하고 worker 1개가 처리한다. 프로세스 메모리의 `setTimeout`이나 요청 후 일회성 background task만으로 큐를 대체하지 않는다. Redis·Celery는 이번 범위에 추가하지 않는다.

작업은 짧은 트랜잭션으로 claim하고, 네트워크 호출 동안 DB 쓰기 트랜잭션을 열어 두지 않는다. 실행 중 lease와 시작 시각을 기록한다. worker가 종료된 작업은 재시작 시 제한된 재시도 1회 후 실패 처리하며 영구 ‘검사중’ 상태를 남기지 않는다. 작업 결과 저장 직전에 앱 존재와 `url_version`이 동일한지 확인한다. 삭제되었거나 URL이 변경되었으면 결과를 버린다.

전체 배치는 시작 시점의 앱 집합을 고정하고 대상별 연결 기록을 남긴다. 기존 개별 작업이나 cooldown 결과를 재사용한 대상도 배치 집계에 포함한다. 같은 실제 작업을 여러 요청이 참조해도 외부 호출은 하나만 실행한다. 검사 도중 새로 등록된 앱은 다음 배치 대상이며, 삭제된 앱은 취소된 대상으로 집계한다.

프론트엔드는 화면을 보고 있을 때만 진행 상태를 제한적으로 polling한다. 화면 이탈·완료·오류 시 polling을 종료한다. 전체 검사는 같은 화면에서 행별 상태를 갱신하며 별도 관리 화면을 새로 만들지 않는다.

## 9. 데이터 모델

내부 ID는 서버가 발급하는 UUID 문자열을 기본으로 한다. 프론트엔드의 별명이나 로그인 아이디를 외래키로 사용하지 않는다. 날짜·시간은 UTC ISO 8601로 API에 반환한다.

### 9.1 주요 테이블

| 테이블 | 주요 필드 | 제약·비고 |
|---|---|---|
| `users` | `id`, `login_id`, `login_id_key`, `password_hash`, `nickname`, `email`, `phone`, `role`, `approved`, `must_change_password`, `created_at`, `updated_at` | `login_id_key UNIQUE`; role는 user/admin; 선택값 NULL; 승인 기본 false |
| `sessions` | `token_hash`, `user_id`, `kind`, `csrf_token`, `created_at`, `authenticated_at`, `expires_at`, `revoked_at` | 세션 식별자 원문 저장 금지. CSRF 토큰은 인증 쿠키와 별개의 난수. 익명 CSRF용 세션만 `user_id=NULL` 허용 |
| `apps` | `id`, `owner_id`, `name`, `url`, `url_version`, `subject`, `prompt`, `description`, `stack_db`, `stack_backend`, `stack_frontend`, `stack_hosting`, `is_public`, `theme_id`, `version`, `created_at`, `updated_at` | owner FK; theme·subject 검증; version으로 동시 수정 충돌 확인 |
| `app_grades` | `app_id`, `grade_code` | 복합 PK; 앱 삭제 CASCADE; grade_code 검증 |
| `app_health` | `app_id`, `url_version`, `state`, `http_status`, `response_ms`, `checked_at`, `error_kind`, `final_url` | 앱당 마지막 완료 결과 1개; 미검사/무응답 값은 NULL; 비권한 응답에 기술 상세 제외 |
| `health_jobs` | `id`, `app_id`, `url_version`, `requested_by`, `status`, `attempts`, `created_at`, `started_at`, `lease_until`, `finished_at`, `failure_code` | app별 활성 작업 중복 방지; 익명 요청자 user ID는 NULL |
| `health_batches` | `id`, `requested_by`, `created_at`, `finished_at`, `target_count` | 전체 검사 대상 집합과 완료 집계의 기준 |
| `health_batch_items` | `batch_id`, `app_id`, `job_id`, `disposition` | 배치별 대상. 새 작업·기존 작업 재사용·cooldown 결과 재사용·취소 구분. 삭제된 app/job 참조는 NULL 처리 가능 |

`apps → users`, `app_grades/app_health/health_jobs → apps`, 로그인 세션→사용자의 삭제 관계를 명시한다. 감사 기록은 삭제된 대상의 식별자가 남을 수 있으므로 사용자 삭제 CASCADE를 적용하지 않고 최소한의 비식별 행위 정보만 보관한다. 영구 삭제와 백업 보관 정책은 13절에 따른다.

권장 인덱스는 `users(login_id_key)`, `users(approved, created_at)`, `apps(created_at, id)`, `apps(owner_id, created_at)`, `apps(is_public, subject, created_at)`, `app_grades(grade_code, app_id)`, `sessions(user_id, expires_at)`, `health_jobs(status, created_at)`다. 실제 쿼리 계획과 시험 결과로 조정한다.

### 9.2 SQLite 운용 계약

모든 연결에서 `foreign_keys=ON`을 명시하고 검증한다[R07]. WAL 모드와 제안 `busy_timeout=5000ms`를 사용한다. WAL도 무제한 동시 쓰기를 제공하는 것은 아니며, 같은 호스트의 로컬 파일시스템에서 운용한다[R08]. 네트워크 파일시스템의 DB 공유·임시 컨테이너 파일에만 저장·여러 서버 간 파일 동기화는 하지 않는다.

쓰기 트랜잭션을 짧게 유지하고, 네트워크 호출·비밀번호 해싱을 트랜잭션 밖에서 수행한다. 각 요청/작업의 DB 세션을 공유하지 않는다. 잠금 실패는 통제된 503/재시도 안내로 변환하며 무한 재시도하지 않는다. migration은 서비스 시작과 분리된 명령으로 먼저 수행한다.

## 10. API 계약

### 10.1 공통 규칙

기본 경로는 `/api/v1`이며 JSON 필드는 snake_case를 사용한다. 원본 컴포넌트의 camelCase는 프론트엔드 mapper에서 변환한다. ORM 모델을 그대로 직렬화하지 않고 공개/본인/관리자 응답 스키마를 분리한다.

입력은 허용 필드만 받는다. `password_hash`, `owner_id`, `role`, `approved`, `health`, `created_at`처럼 요청자가 조작하면 안 되는 값은 일반 등록/수정 스키마에서 제외한다. 공개 앱 DTO에 로그인 아이디·이메일·연락처를 넣지 않는다. 권한이 달라지는 응답은 `Cache-Control: private, no-store`를 기본으로 한다.

표준 오류 형태:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "필수 항목을 확인해 주세요.",
    "fields": {"nickname": "별명을 입력해 주세요."},
    "request_id": "server-generated-id"
  }
}
```

주요 상태 코드는 400 잘못된 요청, 401 인증 필요/실패, 403 승인·역할·CSRF 제한, 404 없음/비공개 비노출, 409 중복/버전 충돌, 422 필드 검증, 429 속도 제한, 503 작업 기능 불가/일시 DB 문제다. 실패 응답을 성공 토스트로 처리하지 않는다.

## 11. 프론트엔드 전환 구조와 환경 설정

### 11.1 화면과 데이터 소스의 분리

기존 화면은 API URL·localStorage 구조·DB 필드명을 직접 알지 않게 한다. `authService`, `appsService`, `adminService`, `healthService`를 통해 같은 비동기 인터페이스를 호출한다. mock 구현도 Promise를 반환하여 원본의 동기 `onLogin/onSave` 반환값을 실제 API로 바꿀 때 화면을 다시 만들지 않게 한다.

`VITE_DATA_MODE=mock`은 원본 데이터 기반의 독립 데모다. `api`는 실제 서버만 사용한다. **운영에서 API 실패를 mock 성공으로 대체하지 않는다.** 한 화면에서 실제 회원과 가짜 관리자/가짜 검사 결과를 혼합하지 않는다.

개발 중에는 mock 모드의 전체 UI가 계속 동작한다. api 모드는 각 phase에서 구현한 기능만 제공하며, 미구현 기능은 `/meta` capabilities에 따라 기존 버튼의 비활성/준비 중 안내로 나타낸다. 부분 API 모드는 개발·검수 전용이며 최종 배포에는 모든 필수 기능이 연결되어야 한다.

mock 회원 자격증명은 개발 fixture에만 둔다. 운영 회원·비밀번호·선택 개인정보는 localStorage에 저장하지 않는다. 운영 빌드에서는 mock 계정·fixture·Tweaks가 포함되지 않았는지 검사한다. 기존 `eduvibe-archive-coty2026` 데이터가 있는 경우 운영 전환 시 이를 서버로 전송하지 않고 해당 데모 저장 키만 제거한다. 다른 앱의 localStorage를 일괄 삭제하지 않는다.

로그아웃·세션 만료·사용자 변경 시 Query 캐시와 진행 요청을 정리한다. 사용자마다 다른 목록의 query key에는 내부 사용자 ID/권한 범위를 포함한다. 이전 회원의 비공개 자료가 다음 회원에게 잠깐 표시되지 않도록 한다.

### 11.3 환경 변수 — 제안값

백엔드와 프론트엔드 `.env`를 분리한다. 비밀은 프론트엔드에 전달하지 않는다. Vite의 `VITE_*` 값은 브라우저 번들에 노출되므로 API 키·DB 경로·비밀번호를 넣지 않는다[R11]. 본 제품은 LLM API를 호출하지 않으므로 모델 ID·LLM API 키 설정을 요구하지 않는다.

```dotenv

VITE_DATA_MODE=mock

```

상대 DB 경로는 실행 위치에 따라 달라질 수 있으므로 서버 설정에서 절대 경로로 해석하고 시작 로그에는 민감 정보 없이 적용 상태만 남긴다. 운영은 `APP_ENV=production`, 영속 볼륨의 절대 DB 경로, HTTPS origin, `COOKIE_SECURE=true`, api 전용 프론트엔드 빌드가 필요하다. 보안 검사 미완료 상태에서 `HEALTH_CHECK_ENABLED=true`로 전환하지 않는다.

운영 빌드의 mock/Tweaks 플래그는 CI가 검사하고, 서버는 insecure cookie·개발 origin 등 운영 부적합 설정이면 시작을 거부한다. `.env`, DB, 백업, 운영 자격증명을 Git이나 정적 파일에 포함하지 않는다.

## 12. 단계별 개발 계획과 통과 조건

각 phase는 실행·시연·테스트 가능한 결과물을 낸다. 앞 단계 통과 전에 다음 단계의 기능 개발을 묶어 진행하지 않는다. 단계 안에서도 읽기→생성→수정→삭제 등 작업 단위별로 연결하고 확인한다.

### Phase 1 — 기존 UI/UX 먼저 구동

**목표:** 백엔드·DB가 없어도 전체 화면을 탐색하고 데모 상호작용을 확인한다.

1. 첨부 원본을 `docs/reference`에 변경 없이 보관하고 원본 실행 기준 캡처를 확보한다.
2. Vite에서 원본 JSX·CSS·아이콘을 실행한다. window 전역 연결만 모듈로 정리하고 UI 재설계는 하지 않는다.
3. 갤러리·로그인·회원가입·상세·등록·편집·관리자 2개 탭·확인/오류 상태를 mock으로 연결한다.
4. 회원가입 추가 필드, 별명 표시, 실제 API 연결에 필요한 공통 로딩/오류 표현을 구현하고 허용 변경 목록에 기록한다.
5. URL 라우팅과 동일한 비동기 서비스 인터페이스를 만든다. 실제 외부 URL 검사나 운영 개인정보 처리는 하지 않는다.

**통과 조건:** 백엔드를 종료한 상태에서 모든 화면이 열린다. mock 가입·승인·로그인·앱 작성·수정·삭제·공개 전환을 재현한다. mock 데이터·시간·검사 결과는 테스트에서 결정적으로 고정한다. 데스크톱/태블릿/모바일 캡처에서 허용 변경 외의 시각 차이가 없다. 필수 입력·오류·취소 흐름을 확인한다.

**개발자가 제공할 명령 계약:** `cd frontend && npm ci && npm run dev`. 해당 명령을 지원하는 프로젝트를 이 단계에서 구현해야 하며, 본 문서에 실행 가능한 앱이 포함되어 있다는 뜻은 아니다.

**이 단계에서 하지 않는 일:** 운영 DB 설계 구현, 실제 인증, 실제 관리자 계정 생성, 외부 HTTP 검사, 배포 인프라 구축.

### Phase 2 — FastAPI·SQLite와 읽기 기능

**목표:** 같은 갤러리·상세 화면에 실제 DB 데이터를 표시한다.

FastAPI 프로젝트, migration, DB 연결, `/meta`, `/apps`, 상세, `/healthz`, `/readyz`를 구현한다. 개발 DB에만 명시적으로 샘플을 주입한다. 검색·필터·과목 집계·페이지 로딩을 연결한다. 이 단계의 API 모드는 공개 데이터 읽기만 가능하며 아직 인증되지 않은 비공개 앱은 절대 반환하지 않는다.

**통과 조건:** 서버 재시작 후 데이터 유지, 필터 복합 적용, 한글 검색, 0건/오류 구분, 비공개 자료·개인정보 비노출, UI 회귀 통과. 샘플 seed 명령을 다시 실행해도 중복되지 않으며 운영 자동 seed가 없다.

### Phase 3 — 실제 회원가입·승인·로그인

**목표:** 실제 계정으로 정상 이용을 시작할 수 있다.

가입 스키마·비밀번호 해시·CSRF·세션·로그아웃·`me`·역할 검사를 구현한다. 최초 관리자 생성 CLI와 **기존 관리자 사용자 탭의 목록/승인/승인 해제**까지 함께 연결한다. 이를 뒤 단계로 미뤄 가입자가 계속 대기 상태에 갇히지 않게 한다. 관리자 기본 통계도 실제 값으로 제공한다. 앱 쓰기·비밀번호 초기화·계정 삭제·실제 검사는 아직 연결하지 않는다.

**통과 조건:** 가입→대기 확인→관리자 승인→로그인→새로고침 유지→로그아웃을 E2E로 통과한다. 아이디와 별명이 다른 계정, 별명 중복, 선택값 미입력/입력/형식 오류를 검증한다. 승인 해제 시 기존 세션이 즉시 차단된다. 일반 회원의 관리자 API 호출은 실패한다.

### Phase 4 — 앱 등록·편집·삭제·공개 범위

**목표:** 회원이 기존 등록 폼으로 실제 아카이브를 관리한다.

등록부터 연결하고 성공 후 상세 조회를 확인한다. 이후 편집, 공개/비공개, 삭제 순으로 구현한다. 소유권·필드 제한·idempotency·version 충돌·캐시 정리를 포함한다. 연결 상태는 `unchecked`로 저장하고 아직 가짜 검사를 보여주지 않는다.

**통과 조건:** 회원 A가 만든 공개/비공개 앱을 비회원·회원 A·회원 B·관리자로 각각 검증한다. 직접 API 요청으로 소유권을 우회할 수 없다. 중복 생성·동시 편집·삭제 후 접근·계정 전환 캐시 누출 시험을 통과한다. 프롬프트 복사와 앱 열기는 기존 UI에서 동작한다.

### Phase 5 — 관리자 기능 완성

**목표:** 기존 대시보드의 계정·앱 운영 기능을 모두 연결한다.

비밀번호 초기화·첫 로그인 변경, 계정 및 소유 앱 일괄 삭제, 모든 앱 편집/삭제, 관리자 계정 보호, 최근 인증 확인, 최소 감사 기록을 구현한다. 사용자/앱 수는 전체 DB 집계이며 미검사 앱을 정상으로 계산하지 않는다.

**통과 조건:** 초기화 전 세션 사용 불가, 임시 비밀번호 로그인 후 변경 전 회원 작업 불가, 계정 삭제의 원자성, 삭제 예상 앱 수 변경 시 재확인, 관리자 계정 금지 작업 거부, 통계 동기화를 검증한다.

### Phase 6 — 실제 HTTP 연결 검사

**목표:** 기존 연결 상태 패널과 Health Monitor에 실제 관찰 결과를 표시한다.

먼저 SSRF 보호와 결과 분류를 모의 transport로 검증한다. 이후 제한된 공개 테스트 URL로 개별 검사, 관리자 전체 검사 순서로 연결한다. SQLite 큐·worker·동시성·cooldown·진행 조회·URL 변경 경합을 구현한다.

**통과 조건:** 200/204/404/403/500, DNS 실패, TLS 실패, timeout, 405→GET, 정상 리다이렉트, 내부망 리다이렉트 차단, URL 교체 중 완료, 앱 삭제 중 완료, worker 중단/재시작을 시험한다. 무작위 상태가 운영 경로에서 사용되지 않는다. 보안 방어 검증 전 실제 검사 기능을 공개하지 않는다.

### Phase 7 — 배포·복구·최종 검수

**목표:** 운영 환경에서 같은 UI와 모든 필수 기능이 지속적으로 동작한다.

정적 프론트엔드·FastAPI 동일 출처 배포, HTTPS, 영속 DB, worker 관리, migration, 백업/복원, 로그·비밀 제외, 전체 E2E·시각·접근성 검수를 수행한다. 개인정보 안내·운영 연락 방식·보관 정책은 공개 전에 담당자가 확정한다.

**통과 조건:** 서버 재시작 후 회원·앱 유지, 깊은 경로 새로고침, 백업 복원 후 데이터 무결성, mock/데모 자격증명/Tweaks 미포함, 비공개 자료 및 선택 개인정보 비노출, 모든 필수 기능 연동, 승인되지 않은 UI 차이 0건.

### 13.2 성능 — 보장값이 아닌 초기 검수 목표

초기 시험 데이터는 사용자 1,000명·앱 5,000개를 제안한다. 2 vCPU/4GB RAM급 단일 호스트를 기준으로 읽기 동시 사용자 50명 조건에서 외부 검사와 로그인 해싱을 제외한 목록·상세 API p95 500ms 이하를 목표로 한다. 측정 환경·DB 크기·쿼리·표본 수를 함께 보고한다. 이 수치를 SQLite의 검증된 처리 용량이라고 주장하지 않는다.

전체 목록을 매번 내려받거나 첫 화면에서 모든 앱을 검사하지 않는다. 검색·목록은 페이지 단위로 읽고 상태 조회도 필요한 화면에서만 수행한다. 비밀번호 해싱과 쓰기 부하는 별도 시험한다. 실제 목표를 충족하지 못하면 쿼리·인덱스·작업량부터 조정하고, DB 교체는 별도 의사결정으로 남긴다.

### 13.3 개인정보·로그

이메일·연락처의 수집 목적·보유 기간·운영자 열람 필요성은 원본에 없다. 제안 목적은 서비스 운영상의 개별 연락이며, 실제 목적과 개인정보 안내/동의 방식은 운영자가 공개 전에 확정해야 한다. 선택값을 입력하지 않은 이용자의 가입·승인·앱 등록을 불리하게 제한하지 않는다. 개인정보 관련 법적 요건을 이 문서만으로 충족했다고 간주하지 않는다.

요청 로그는 request ID·경로 템플릿·상태·처리 시간 중심으로 남긴다. 비밀번호·해시·세션/CSRF 토큰·email/phone·전체 요청 본문·민감 query URL을 로그에 기록하지 않는다. 운영 DB와 백업은 접근 권한과 저장장치/백업 암호화 정책으로 보호한다. SQLite 파일 자체가 자동 암호화된다고 가정하지 않는다.

감사 기록은 제안 90일, 백업은 제안 30일을 기본으로 하되 공개 전 확정한다. 개인정보 삭제 후에도 보관 중 백업에 과거 값이 남을 수 있으므로, 보관 만료·복원 후 삭제 재적용 정책을 함께 정한다. 일반 UI의 ‘되돌릴 수 없음’은 서비스 내 복구 기능이 없다는 의미이지 모든 백업에서 즉시 물리 삭제된다는 보장이 아니다.

### 13.4 배포·백업

운영은 HTTPS와 동일 출처를 기본으로 한다. CORS를 사용해야 하는 예외 환경에서는 허용 출처를 명시하고 자격증명 요청에 wildcard를 사용하지 않는다. `.env`, SQLite 파일·WAL·SHM, 원본 데모, 백업 파일을 정적 루트 밖에 둔다. 미확인 `/api/*`와 존재하지 않는 정적 asset 요청을 SPA HTML로 응답하지 않는다.

제안 백업 주기는 매일 1회 및 migration 직전이다. 온라인 백업 API 등 일관성 있는 방법을 사용하고, 실행 중인 DB의 `.sqlite3` 파일 하나만 임의 복사하지 않는다[R08][R12]. RPO 24시간·RTO 4시간은 초기 목표이며 복구 연습으로 검증해야 한다.

복원은 별도 환경에서 무결성과 외래키를 확인한 후 적용한다. 복원 시 세션을 모두 폐기하고 폐기되어야 하는 계정/자료의 삭제 상태를 재검증한다. 디스크 용량·DB 잠금 오류·worker 생존·백업 성공 여부를 운영 점검 항목으로 남긴다.

## 14. 구현 작업 분해와 완료 정의

### 14.1 작업 단위 원칙

각 작업에는 연결할 화면·서비스 메서드·API·데이터 제약·권한·테스트·시연 방법을 명시한다. 단순히 ‘백엔드 전체 구현’이나 ‘관리자 화면 완성’으로 묶지 않는다. 앱 등록은 API만 성공하면 완료가 아니라 기존 폼→저장→DB→상세 조회→새로고침까지 확인해야 한다.

### 14.2 첫 개발 작업 지시문

```text
첨부 EduVibe HTML/JSX와 PRD의 Phase 1만 구현한다.
기존 UI/UX를 새로 디자인하지 않는다.
원본 파일을 reference로 보관하고, Vite에서 화면을 먼저 실행한다.
기존 JSX/CSS의 모양을 유지하면서 import/export와 라우팅을 정리한다.
모든 화면과 데모 동작은 Promise 기반 mock service를 사용한다.
회원가입은 아이디·비밀번호·비밀번호 확인·별명·선택 이메일·선택 연락처를 받는다.
아이디가 아니라 별명이 공개 위치에 표시되도록 한다.
실제 FastAPI·DB·외부 HTTP 검사·운영 개인정보 수집은 아직 연결하지 않는다.
실행 명령, 화면별 시연 순서, 테스트 결과, 원본 대비 허용 변경 목록을 제출한다.
Phase 1 시각 검수와 동작 검수가 통과되기 전 Phase 2를 구현하지 않는다.
```

### 14.3 최종 완료 조건

사용자 요구 필드로 가입한 사람이 관리자 승인 후 로그인하고, 제공된 UI에서 앱을 등록·편집·공개 전환·삭제할 수 있어야 한다. 비회원은 공개 앱을 검색·열람·복사·열 수 있어야 한다. 관리자는 기존 대시보드에서 계정·앱·연결 상태를 관리할 수 있어야 한다. 모든 권한 판단과 저장은 서버·SQLite가 담당하고 실제 상태를 표시해야 한다.

전 phase 테스트와 허용 변경 외 시각 회귀가 통과하고, 운영 빌드에 mock·공개 데모 비밀번호·Tweaks가 없어야 한다. 배포·migration·백업·복원 절차가 재현 가능해야 한다. 소스 검토만으로 완료 처리하지 않는다.

## 15. 공개 전 확정할 운영 사항

개발을 위한 기본값은 본문에 있으므로 UI 착수는 바로 가능하다. 다음 항목은 원본이나 사용자 요청에 없으며 공개 운영 전에 확정해야 한다.

| 항목 | 본 문서의 처리 |
|---|---|
| 운영 도메인·배포 호스트 | 미지정. 단일 호스트·HTTPS·영속 SQLite를 기준으로 구현 |
| 초기 관리자·분실 계정 본인 확인 방식 | 대화형 bootstrap/복구 CLI 제공, 담당자와 절차는 운영자가 지정 |
| 선택 개인정보 수집 목적·안내·보관·관리자 접근 | 13절 제안안 검토 후 확정. 미확정 상태에서 공개 수집 금지 |
| 비밀번호·아이디·별명 세부 정책 | 6절 제안값으로 구현하고 변경 시 검증/문구 함께 수정 |
| 원본과 축소 이미지 사이 시각 불일치 | 실제 렌더링과 차이 기록을 Phase 1에서 검토 |
| 모바일 관리자 메뉴·새 프로필 화면 | 원본에 없으므로 추가하지 않음. 필요 시 별도 승인 |
| 자동 연결 검사·알림 | 포함하지 않음. 수동 재검사만 구현 |
