## Issue #44 admin reauthentication and member password reset

The existing admin member row opens the shared reauthentication card. A successful reauthentication only returns a target reference; the admin view reads the current member again before displaying an empty masked form. Reset results use the shared operation contract and require explicit result lookup, exact same-key input retry, or cancellation while unresolved. Confirmed success preserves approval, advances the account version, sets the temporary-password deadline, invalidates the mock target session when represented in the current tab, and leads through the existing change-only login to T08 password change.

The temporary password never enters the URL or persistent mock state. The deterministic mock keeps the emulated credential and its operation binding in module memory; a full document reload clears them, so the reset credential works only while the same SPA document remains open. This is a Phase 1 mock limit. The mock does not implement actual HMAC/password hashing, durable operation records, HTTP cookies/CSRF, database transactions, cross-device session invalidation, or password delivery. Reset and reauthentication capability flags remain disabled under the phase gate in [#24 case 28](https://github.com/DomineYH/vibe_coding_archive/issues/24#issuecomment-5806786959); no real capability is advertised.

The issue-specific trace, first red tests, final CI-equivalent commands, five-viewport captures, and the individual [#24 29-case trace](evidence/phase-1/issue44/2026-09-27/README.md) are in the #44 run evidence. Normal reset/T08, unknown and committed-but-response-lost recovery, mismatch, protected/missing/stale target, invalid reauthentication, and delayed stale-auth rejection are exercised in the mock. Concurrent DB races, secret rotation/restore, real session revocation, actual delivery, human UI-D approval, screen-reader/device review, hosted CI, and local handover remain unverified; they are not reported as PASS.
