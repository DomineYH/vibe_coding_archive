# Encrypted local database backups

`python -m app.cli backup-db` creates one private local backup with age v1 native X25519 public recipients. It always reports `LOCAL_ONLY_REMOTE_NOT_CONFIRMED` with exit **3** after local completion. No remote transfer or independent re-query occurs, and there is no remote-confirmation override. Artifact presence, a local ledger checkpoint, and CI encryption tests do not establish VM-loss durability or authorize deployment or restore.

## Invocation and prerequisites

Provision a single backup output namespace per deployment, with an owned 0700 directory. The database and its adjacent `.deletions.sqlite3` ledger must already exist with mode 0600 in an owned 0700 directory. The recipient file is an owned, single-link regular 0600 file in a private directory; it contains only `age1…` native X25519 public recipients, optionally blank lines and comments. Symlinks, hardlinks, unsafe ownership/modes, and writable ancestors are rejected. Root-owned sticky temporary ancestors are accepted only in APP_ENV=test. Production paths must be absolute and outside temporary/repository/static locations. Keep backups away from every web-served directory; the CLI rejects its repository tree and requires private ancestry.

Use the already configured runtime/environment and a trusted installed age v1 executable. Ubuntu provisioning/CI obtains `age` from signed apt indexes and records the resolved package version, `age --version`, and `age-keygen --version`. CI fails when real age tools are missing; local skips are NOT RUN. The command takes no private identity or passphrase. Keep private identities off the application VM, under the separate key-custody process. Never put secrets in paths, release/run identifiers, command arguments, shell history, logs, or shared manifests. Release IDs are bounded letters/digits/dot/underscore/hyphen identifiers; supplied run IDs are canonical UUIDs.

```bash
APP_ENV=production \
DATABASE_PATH=/srv/eduvibe/database/database.sqlite3 \
PUBLIC_ORIGIN=https://archive.example.org \
HEALTH_CHECKS_ENABLED=false \
uv run --frozen python -m app.cli backup-db \
  --output-dir /srv/eduvibe/backups \
  --recipient-file /srv/eduvibe/backup-config/recipients.txt \
  --release-id release-2026-10-08
```

These are example paths/origin only. Use actual approved operator configuration. Schedule at 07:00 and 19:00 KST and invoke before each explicit migration; T05 owns scheduling. A scheduler must distinguish exit 3 from operational backup success. HEALTH_CHECKS_ENABLED=false remains the handoff configuration; this command creates no activation or approval record.

| Exit | Meaning |
|---|---|
| 3 | Valid local pair published; independent remote confirmation absent |
| 1 | Runtime, verification, lock, encryption, or publication failure |
| 2 | Usage/configuration error (also help; no backup command path returns 0) |
| 130 / 143 | Handled SIGINT / SIGTERM |

Errors use fixed safe messages, without raw exception values or age stderr. A missing tool/recipient/ledger, incompatible revision, or uncertain publication cannot be reported as success. Retry a failed attempt with a new run ID after resolving its cause.

## Payload and manifest v1

The output root contains a persistent owned 0600 `.backup.lock`, hidden owned 0700 `.stage-…` directories during attempts, and published owned 0700 UUID directories. A complete UUID directory contains exactly `backup.tar.age` and `manifest.json`, both 0600. The pair becomes visible by directory rename after successful encryption and file/directory fsync; the parent directory is also fsynced. Consumers ignore hidden stages.

SQLite's online backup API captures the live WAL database into a stable in-memory copy, while ordinary API writes can continue. No live main-file cp or WAL/SHM copying occurs. The copy must pass integrity, foreign-key, Alembic-head, and essential app/ownership/grade/health relationship checks. This command never migrates, repairs, delivers deletion events, or changes the source/ledger.

The decrypted tar has exactly two regular 0600 members: `database.sql` and `metadata.json`. `payload_format` is **sqlite-sql-dump-v1**. `database.sql` contains the UTF-8 logical SQL dump generated by `Connection.iterdump()` from the validated copy, including `alembic_version`, all table rows, indexes and triggers. The `database.sha256` and `database.bytes` manifest fields describe the exact SQL dump bytes, including its final newline, rather than the live SQLite file. The current schema has no virtual/FTS tables or nonzero PRAGMA user_version/application_id; the command fails if that premise changes. Tests protect the premise and compare every restored table with the captured snapshot.

T04 must decrypt into memory and execute this dump in a **fresh empty isolated SQLite target**, then check integrity, foreign keys, revision, dump hash/size and the authenticated inner metadata. The dump is executable SQL: restoration belongs to the separately authorized restore workflow, with its own trust boundary and current deletion evidence. This ticket adds no restore command.

The immutable manifest core contains format/payload versions, run ID, UTC creation/recovery/snapshot-completion timestamps, original expiry, release/revision/age version, recipient-file SHA-256, `included: ["main_database"]`, SQL dump hash/size, and the deletion checkpoint. The outer manifest additionally contains ciphertext SHA-256/size, `local_complete: true`, `remote_confirmed: false`. It contains no source paths, row IDs, payload text, cookies, contact information, credentials, or raw recipients/identities.

`validate_manifest(manifest)` checks structure and expiry only. Authenticity requires age-authenticated decrypted `metadata.json` to equal the outer core; `validate_manifest(manifest, metadata=inner)` checks that equality. Verification also checks ciphertext and dump hashes/sizes. Unkeyed hashes alone cannot establish authenticity. An attacker holding a public recipient can replace an entire pair; T10 must supply trusted external inventory to detect whole-pair substitution.

Creation and conservative recovery point are recorded immediately before the fixed online snapshot. Original expiry is exactly creation + 30 days. Encryption, retry, upload or copying never refreshes that lifetime. Duplicate run IDs are rejected without changing prior artifacts. Row/credential retention deadlines in the dump remain unchanged. T06 owns proactive 29-day cleanup and the complete copy inventory.

## Deletion continuity

The adjacent independent deletion ledger is read in one read-only transaction after the main snapshot is fixed. The checkpoint records schema version 1 of this supported checkpoint shape, UTC observation time, and canonical counts/digests for all six supported ledger tables, including empty tables. Rows are hashed privately and never emitted. No synthetic cursor or mtime continuity claim is made.

Snapshot legacy mirrors and app/account deletion outboxes must match existing independent events, including undelivered snapshot events; account groups must be complete. Missing, conflicting, partial or incompatible evidence fails closed without repair. Later complete ledger events are allowed. A concurrent deletion can therefore make an attempt fail safely; retry later with a new UUID.

The ledger is **not included in the archive**, and the checkpoint is a local historical reference only. Never restore/roll back the live ledger to this checkpoint. T04 needs the latest independently retained deletion evidence; T10 owns external ledger durability, trusted inventory and remote re-query confirmation. A same-host ledger cannot prove survival of VM loss.

## Interruption, memory and cleanup

Production creates no plaintext DB/dump/archive file, including in staging. Snapshot, logical dump and tar input stay in process memory. Core dumps are disabled by the CLI. Disable or encrypt host swap before making a stronger plaintext-at-rest claim; the CLI cannot verify host policy. Allocation failure has no disk fallback.

<!-- ponytail: RAM scales with DB size; evaluate protected tmpfs separately when target-scale memory is insufficient. -->
RAM includes the SQLite copy and UTF-8 dump/encoding buffers. The target is 1,000 members / 5,000 apps; measure representative synthetic sizes before operational adoption. A synthetic small-prompt 1,000-member / 5,000-app measurement produced a 4,153,344-byte SQLite copy and 2,943,941-byte dump; the measurement process peaked at 45,544 KiB RSS, including an in-memory restore but excluding full CLI/application imports. Larger prompts increase memory beyond row-count estimates.

SIGINT/SIGTERM, child failures/timeouts, broken pipes, ENOSPC and fsync errors close handles, reap the encryptor and remove the current unfinished stage when possible. Previous published runs are preserved. SIGKILL/OOM may leave a private ciphertext-only stage; no cleanup is promised after uncatchable termination. A parent-fsync failure after rename reports failure but preserves the published pair for inspection. Do not overwrite/reuse that UUID or assume its durability.

For stale-stage cleanup, stop scheduling, verify the old process has exited, acquire the existing persistent `.backup.lock` with exclusive flock, inspect hidden stage ownership/modes and remove only the identified unfinished stage. Do not remove the lock inode, source database, independent ledger, UUID runs, or unrelated stages. Ciphertext created before an interrupted age process completes may be invalid. This ticket provides no garbage collector or automated restore authorization.
