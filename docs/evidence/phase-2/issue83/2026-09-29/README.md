# Issue #83 implementation and verification evidence

## Scope and revision

Issue [#83](https://github.com/DomineYH/vibe_coding_archive/issues/83), under Phase 2 spec [#77](https://github.com/DomineYH/vibe_coding_archive/issues/77), connects the real public detail response to the existing detail screen and keeps gallery return behavior, copy failure, and unavailable-health meaning explicit. It follows the approved decisions in [#7](https://github.com/DomineYH/vibe_coding_archive/issues/7), [#8](https://github.com/DomineYH/vibe_coding_archive/issues/8), [#11](https://github.com/DomineYH/vibe_coding_archive/issues/11), [#12](https://github.com/DomineYH/vibe_coding_archive/issues/12), [#15](https://github.com/DomineYH/vibe_coding_archive/issues/15), and [#29](https://github.com/DomineYH/vibe_coding_archive/issues/29).

The source/test commit is [`556f73cefdacdf959612e39247dd1ce90fb29d47`](https://github.com/DomineYH/vibe_coding_archive/commit/556f73cefdacdf959612e39247dd1ce90fb29d47). Detail routing rejects malformed IDs and unsupported query strings before requesting detail data; query recovery is an explicit reset. The real API service and shared mapper remain the source of successful detail content. No OpenAPI contract, generated type, lockfile, source reference, visual baseline, or production backend behavior changed.

## Environment and API fixture

- Node 22.23.2, npm 12.0.2, Playwright 1.63.0, pinned headless Chromium 151.0.7922.34.
- Five viewports at DPR 1: 1440×1000, 1024×900, 768×1024, 390×844, and 360×844.
- `npm run test:e2e:api` runs the real FastAPI process against a temporary file SQLite database. Its opt-in synthetic fixture makes existing public row 1 contain long name/nickname/URL/description/prompt values, selected grades and stack fields, a date, and literal HTML sentinels. The fixture does not add rows or change inherited paging totals. The temporary database is removed when the runner exits.
- API success comes from FastAPI and SQLite. Playwright intercepts only the explicitly identified transport/contract/clipboard failure cases; each recovery path is checked separately. Browser requests outside loopback are blocked. No raw database, credentials, or production user content is included here.
- The final API run captured 35 screenshots (seven states × five viewports) under [visual/api-mode](visual/api-mode/): detail success, invalid detail query, detail not found, detail transport error, detail contract error, copy success, and copy failure. For example: [detail success at 1440×1000](visual/api-mode/detail-1440x1000.png), [detail transport error at 1440×1000](visual/api-mode/detail-network-error-1440x1000.png), and [copy failure at 1440×1000](visual/api-mode/detail-copy-failure-1440x1000.png). The filenames encode state and viewport.
- The API E2E runner also rewrote screenshots in the existing #81/#82 directories; those exact directories were restored after the final run. No unrelated image remains changed.
