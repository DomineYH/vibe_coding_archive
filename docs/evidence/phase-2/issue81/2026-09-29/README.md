# Issue #81 implementation and verification evidence

## Scope and revisions

Issue [#81](https://github.com/DomineYH/vibe_coding_archive/issues/81), under [Phase 2 spec #77](https://github.com/DomineYH/vibe_coding_archive/issues/77), completes the public list query contract and activates the existing `apps_read` capability. The implementation is commit [`e09fecc`](https://github.com/DomineYH/vibe_coding_archive/commit/e09fecc), followed by test-boundary commit [`ad6b4ea`](https://github.com/DomineYH/vibe_coding_archive/commit/ad6b4ea). The follow-up only adds acceptance-boundary assertions; API and frontend runtime code are unchanged.

Search trims ECMAScript whitespace, applies NFC and Unicode casefold, enforces 100 folded code points, and performs literal substring matching independently on public app name, owner nickname, and description. Subject and grade filters combine with search using AND. The route strictly parses raw query bytes, rejects repeated and unknown keys, invalid percent/UTF-8, invalid filters and numeric values, and does not clamp limits. Ordering remains `created_at DESC, id DESC`; totals and pages use the filtered set, while subject facets use the complete public set in catalog order.

The OpenAPI source and generated TypeScript already declared `q`, `subject`, `grade`, `limit`, and `offset`, so neither file was edited. A backend HTTP contract test compares every FastAPI list parameter and normalized schema to that source. `apps_read` is enabled only after list/detail, query, and redaction checks pass; other capabilities retain their prior disabled reasons. Public responses expose no login, contact, password, prompt-only, private-row, or health-job data. The UI receives real owner nicknames and stored `unchecked` health, and makes no auth, CSRF, health, write, or administrator calls.

TDD evidence: before implementation, the added list-query contract tests failed against the old route (3 failed, 18 passed). The implementation then passed the focused search/filter/API declaration tests and the complete contract suite. The first API browser run exposed invalid all-zero UUIDs in the shared test fixture; API E2E now opts into valid synthetic UUIDs to satisfy the existing strict frontend mapper. Subsequent failures were corrected test locators, not server behavior. The final actual API browser run passes 3/3.

## Test data and visual evidence

The API E2E wrapper migrates and owns a temporary file SQLite database and seeds 27 public synthetic apps plus a private sentinel row. It does not call the development seed or persist data. The public/detail browser flow checks real metadata and list responses, a composite query (`q` + subject + grade), the next page, normal zero results, private detail 404, detail reload and return, unchecked health, explicit list retry after a 503, no auth/CSRF/health endpoint call, and blocked external requests.

The [API-mode capture directory](visual/api-mode/) contains 45 full-page PNGs for the public gallery, composite-filtered results, zero results, detail, list error, metadata failure, and held loading state at the five fixed viewports. The [comparison record](visual/api-mode/comparisons.json) has 35 records; all five viewports are included. Synthetic card content changes page height, so gallery, filtered, and detail comparisons record dimensions without padding or pixel claims. Zero-result and list-error screens are pixel-compared with their mock references. Metadata failure/loading match the prior API state at four viewports; their 390×844 captures each differ by 16 pixels. These differences remain visible for human UI-D review; `human_approval` is pending. No visual baseline or source reference changed.

The API browser tests use accessible names/roles for search, filters, links, retry, and page controls, check that the document does not overflow each viewport, verify keyboard retry focus during metadata loading, and assert `rel="noopener noreferrer"` on the external app link. These desktop Chromium checks do not constitute physical-device, screen-reader, or human visual approval.
